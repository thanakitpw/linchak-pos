| | **Platform admin** | **สิทธิ์ในร้าน** |

## 1. Platform admin (`/admin`)

### 1.1 ใครเข้าได้

2 ระดับ เก็บใน `platform_admins.role`

| | `superadmin` | `support` |
|---|---|---|
| ดูรายชื่อร้าน + สถิติ | ✓ | ✓ |
| บันทึกการชำระเงิน / ต่ออายุ | ✓ | ✓ |
| ระงับ / ปลดระงับร้าน | ✓ | ✗ (ขอ superadmin) |
| ลบข้อมูลร้าน | ✓ | ✗ |
| เพิ่ม/ถอด platform admin | ✓ | ✗ |
| ดู audit log | ✓ | ✓ (เฉพาะของตัวเอง) |
| impersonate เข้าไปดูร้าน | ✓ | ✓ (บันทึก audit ทุกครั้ง) |

> MVP มี superadmin คนเดียวก็พอ (คุณ) แต่แยก role ไว้ตั้งแต่แรกจะถูกกว่าเติมทีหลัง
> เพราะ RLS policy ที่เขียนโดยไม่มี role จะต้องรื้อทั้งหมด

### 1.2 หน้าจอ

| หน้า | มีอะไร |
|---|---|
| **Dashboard** | จำนวนร้านแยกตามสถานะ · MRR · สมัครใหม่สัปดาห์นี้ · **ใกล้หมด trial ใน 3 วัน** · **เลยกำหนดจ่าย** |
| **รายชื่อร้าน** | ค้นหา (ชื่อร้าน/เบอร์/อีเมลเจ้าของ) · กรองตามสถานะ · เรียงตามวันหมดอายุ · แสดง: ชื่อร้าน, เจ้าของ, สถานะ, หมดอายุ, บิลเดือนนี้, ใช้งานล่าสุด |
| **ร้านรายตัว** | ข้อมูลร้าน · สมาชิก + สิทธิ์ · ประวัติการจ่ายเงิน · audit log ของร้านนี้ · ปุ่ม: **ต่ออายุ / ระงับ / ปลดระงับ / impersonate** |
| **บันทึกการชำระเงิน** | ฟอร์ม: เลือกร้าน → แผน → จำนวนเงิน → รอบ (auto จากแผน แก้ได้) → วิธี → เลขอ้างอิง → แนบสลิป → โน้ต · **กดแล้วเปลี่ยนสถานะร้านเป็น `active` + ขยาย `current_period_end` อัตโนมัติ** |
| **Audit log** | ทั้งระบบ กรองตาม actor / action / ร้าน / ช่วงเวลา |
| **ผู้ดูแลระบบ** | (superadmin เท่านั้น) เพิ่ม/ถอด platform admin |

### 1.3 การกระทำหลัก

**ต่ออายุ** = เขียนแถว `payments` แล้ว:
```
current_period_end = max(current_period_end, วันนี้) + plan.period_months
subscription_status = 'active'
```
> ใช้ `max(...)` เพื่อให้จ่ายก่อนหมดอายุแล้วไม่เสียวันที่เหลือ

**ระงับ** — **บังคับกรอกเหตุผล** · เขียน `suspended_at/by/reason` + audit
เหตุผลที่ใช้จริง: ไม่จ่าย, ใช้ผิดเงื่อนไข, ลูกค้าขอปิดเอง, สงสัยฉ้อโกง

**impersonate** — เข้าไปเห็นแอปในมุมของร้านเพื่อช่วย support
- ต้องกรอกเหตุผลก่อน · เขียน audit ทันที · หมดอายุอัตโนมัติใน 30 นาที
- ขณะ impersonate ต้องมี **แถบสีแดงค้างบนจอ** ว่ากำลังสวมสิทธิ์อยู่
- **โหมดอ่านอย่างเดียว** — admin ห้ามออกบิลหรือแก้ข้อมูลแทนลูกค้า

### 1.4 ความปลอดภัย

- `/admin` อยู่ในแอปเดียวกัน แต่ทุกหน้าเป็น **server component + server action** เท่านั้น
- **ห้ามส่ง `service_role` key ลง browser** เด็ดขาด (NFR-4)
- ตรวจ `is_platform_admin()` ที่ชั้น DB ด้วย ไม่ใช่แค่ middleware — middleware หลุดได้ RLS ไม่หลุด
- **ทุก mutation เขียน `audit_logs`** — ไม่มีข้อยกเว้น
- แนะนำบังคับ 2FA สำหรับ platform admin (Supabase Auth รองรับ TOTP)
- โดย default admin **ไม่เห็นข้อมูลบิล/สินค้าของลูกค้า** เห็นแค่ตัวเลขสรุป → ต้อง impersonate ถึงจะเห็นของจริง (ดู `data-model.md` §8 ข้อ 1)

## 2. สิทธิ์ในร้าน (`memberships.role`)

ปัญหาจริงของแม่ค้า: **จ้างเด็กมาช่วยขายหน้าร้าน แต่ไม่อยากให้เห็นกำไร**

| ความสามารถ | `owner` | `manager` | `staff` |
|---|:---:|:---:|:---:|
| ออกบิล | ✓ | ✓ | ✓ |
| ดูบิลย้อนหลัง | ทั้งหมด | ทั้งหมด | เฉพาะที่ตัวเองออก |
| ยกเลิก/แก้บิล | ✓ | ✓ | ✗ |
| ดูสินค้า | ✓ | ✓ | ✓ |
| เพิ่ม/แก้สินค้า | ✓ | ✓ | instant add เท่านั้น |
| ลบ (archive) สินค้า | ✓ | ✓ | ✗ |
| จัดการหมวดหมู่ | ✓ | ✓ | ✗ |
| **บันทึกต้นทุน** | ✓ | ✓ | ✗ |
| **ดูรายงานยอดขาย** | ✓ | ✓ | ✗ |
| **ดูกำไร** | ✓ | ✓ | ✗ |
| ตั้งค่าร้าน (PromptPay/VAT/ภาษา/โลโก้) | ✓ | ✗ | ✗ |
| เชิญ/ถอด/เปลี่ยนสิทธิ์สมาชิก | ✓ | ✗ | ✗ |
| ดูสถานะ/ประวัติการจ่ายค่าบริการ | ✓ | ✗ | ✗ |

**เส้นแบ่งที่สำคัญ:** `staff` ไม่เห็นตัวเลขเงินย้อนหลังเลย — ไม่เห็นต้นทุน ไม่เห็นกำไร ไม่เห็นยอดรวมวัน
เห็นแค่บิลที่ตัวเองเพิ่งออก นี่คือเหตุผลหลักที่ต้องมี role ตั้งแต่แรก

**กฎเสริม**
- ทุกร้านต้องมี `owner` อย่างน้อย 1 คนเสมอ — ถอดคนสุดท้ายไม่ได้
- โอนความเป็นเจ้าของต้องยืนยัน 2 ขั้น
- `staff` ที่ถูกถอดออก บิลที่เคยออกยังอยู่ (`created_by` ชี้ user เดิม)

> PRD ระบุว่าหลายผู้ใช้เป็น "เฟสหลัง" — MVP สร้าง `owner` แถวเดียวพอ
> แต่ **เขียน RLS ให้ตรวจ role ตั้งแต่แรก** เพราะการเติม role ทีหลังแปลว่าต้องรื้อ policy ทุกตาราง

## 3. ลำดับที่ควรทำ

| ลำดับ | ทำอะไร | ทำไมต้องก่อน |
|---|---|---|
| 1 | schema + RLS + ฟังก์ชัน (`data-model.md`) | ทุกอย่างวางอยู่บนนี้ |
| 2 | Auth + สมัคร → สร้าง workspace + membership `owner` | FR-0.1/0.2 |
| 3 | **gate สถานะที่ระดับ DB** (`workspace_is_writable`) | ถ้าทำทีหลัง ต้องกลับมาแก้ policy ทุกตาราง |
| 4 | `/admin` — รายชื่อร้าน + ต่ออายุ + ระงับ + audit | **ถ้าไม่มีอันนี้ ขายไม่ได้** — ลูกค้าโอนเงินแล้วเปิดบัญชีให้ไม่ได้ |
| 5 | หน้าตั้งค่าร้าน (FR-1) | ที่ที่ลูกค้าใส่เลข PromptPay — ไม่มีอันนี้ฟีเจอร์หลักใช้ไม่ได้ |
| 6 | หน้าจอฟีเจอร์ที่เหลือ | |
| 7 | สมาชิก + role UI | เฟสหลังตาม PRD |
| 8 | payment gateway อัตโนมัติ | เมื่อจำนวนลูกค้าทำให้บันทึกมือไม่ไหว |

> **ข้อ 4 มาก่อนหน้าจอฟีเจอร์ส่วนใหญ่** เพราะ business plan §6 บอกว่าขายผ่าน LINE แบบ manual
> ถ้าไม่มีหน้าเปิดบัญชี ต่อให้แอปสวยแค่ไหนก็รับเงินลูกค้าคนแรกไม่ได้

## 4. ที่ต้องตัดสินใจ

1. **`support` role จำเป็นตั้งแต่แรกไหม** — ถ้าทำคนเดียวยังไม่ต้อง แต่ schema รองรับไว้แล้ว
2. **admin เห็นข้อมูลลูกค้าได้แค่ไหนโดยไม่ impersonate** — ผมเสนอ "เห็นแค่ตัวเลขสรุป" (ปลอดภัยกว่าและ PDPA ง่ายกว่า)
3. **ผูก LINE เข้ากับ workspace ไหม** — ทำให้ส่งเตือนใกล้หมดอายุอัตโนมัติได้ แต่มีเรื่อง PDPA
4. **`staff` ควรเห็นยอดรวมของวันไหม** — ตอนนี้ผมตั้งเป็นไม่เห็น ถ้าจะให้ปิดบัญชีสิ้นวันได้อาจต้องเห็น
5. **grace period 3 วัน เหมาะไหม** — ตั้งจากสมมติฐานว่ากดยืนยันการโอนช้าสุด 2 วันทำการ
