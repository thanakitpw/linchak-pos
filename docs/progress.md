## ขั้นถัดไป (เรียงตามที่ควรทำ)

### 1. ปิดช่องโหว่หลัง deploy ← **งานหลักถัดไป**

2. 🔴 **ต่อ SMTP (Resend) + เปิด Confirm email กลับ** — ถ้าไม่ทำ ลูกค้าจริงไม่ได้รับอีเมลเลย
   และตอนนี้ใครก็สมัครด้วยอีเมลคนอื่นได้
3. ตั้ง minimum password length = 8 ใน Dashboard
4. ผูกโดเมนจริงแทน `*.vercel.app`
5. หน้า FR-0.4 ตอน trial หมด (ตอนนี้มีแค่แถบเตือนในหน้าขาย ยังไม่มีหน้าจ่ายเงิน)

### 2. PWA ขั้นที่ 2 — ใช้ตอนเน็ตหลุด (NFR-5 ครึ่งหลัง)
ขั้นที่ 1 (manifest → ติดตั้งลงหน้าจอโฮมได้ เปิดเต็มจอ) **เสร็จแล้ว** ดูเฟส 17
ที่เหลือคือ service worker (`@serwist/next` ยังไม่ได้ติดตั้ง) —
**ต้องตัดสินใจเรื่องออกบิลตอนออฟไลน์ก่อนเริ่ม** เพราะเลขบิลจัดสรรที่ DB (กฎ 27)
· `pb-safe` กับ `100dvh` ยังไม่เคยเจอ iPhone จริง

### 3. หน้าจอที่เหลืออีก 1 หน้า + งานรอง

### เฟส 9 · บิล public (FR-4.6) + QR เปิดบิล (FR-4.3)

- `/r/[token]` — ลูกค้าเปิดจากลิงก์ใน LINE ไม่ต้องล็อกอิน อ่านอย่างเดียว
  อยู่ **นอกกลุ่ม `(app)`** จึงไม่มีแท็บล่าง ไม่มีทางกดเข้าแอป
- **ข้อมูลมาจาก `get_public_receipt()` ตัวเดียว ห้าม query ตารางตรงๆ ในหน้านี้**
  ฟังก์ชันนั้นคือด่านที่ตัดสินใจแล้วว่าอะไรออกไปข้างนอกได้ ถ้า query เองจะเกิดด่านที่สองที่ไม่มีใครตรวจ
- `robots: noindex, nofollow` — ลิงก์เดาไม่ได้ก็จริง แต่ถ้าลูกค้าเผลอโพสต์ลงเว็บบอร์ด
  แล้ว crawler ตามไปเก็บ บิลนั้นจะค้นเจอใน Google ตลอดไป
- token ที่ไม่ใช่รูป uuid ตัดทิ้งก่อนถึง DB (ไม่งั้น Postgres โยน 22P02)
  หน้า 404 ไม่บอกว่าทำไมเปิดไม่ได้ — การแยกเคสให้คนนอกฟังคือการยืนยันว่า token ไหนมีอยู่จริง
- **ภาษาของบิลมาจากร้าน ไม่ใช่จาก cookie ของคนเปิด** — บิลใบเดียวต้องอ่านได้เหมือนกันทุกคน
  แก้ที่ `i18n/request.ts` ให้รับ `requestLocale` และ `ReceiptCard` รับ locale ทาง prop
- **QR เปิดบิลออนไลน์ (FR-4.3)** — ใบเสร็จมี QR **อันเดียว** เสมอ:
  ตั้ง PromptPay แล้ว → QR จ่ายเงิน · ยังไม่ตั้ง → QR เปิดบิล (ตรงตาม AC ของ FR-1.2)
  ไม่ใส่สองอันพร้อมกันเพราะลูกค้าที่เปิดแอปธนาคารมาสแกนจะจับผิดอัน
- ปุ่มล่างใบเสร็จเปลี่ยนจาก "ขายต่อ" เป็น **"ดูบิลออนไลน์"** ตาม mockup `mobile_9`

### เฟส 15 · แก้สีตัวหนังสือบนปุ่มเขียว + หน้าขายเลื่อนลงไม่สุด

รายงานจากการใช้จริงบน iPhone 2 เรื่อง กลายเป็นบั๊กคนละชั้นกันคนละใบ

**1 · ปุ่ม CTA ตัวหนังสือเป็นสีเข้มแทนที่จะเป็นสีขาว — `cn()` ลบ class สีทิ้งเงียบๆ**

`tailwind-merge` ตัว default มองว่า `text-<อะไรก็ได้>` คือ **สีตัวอักษร**
(validator ของกลุ่ม text-color เป็น `isAny` = รับทุกอย่าง)
ขั้น type ของเรา — `text-title-lg`, `text-body-md`, `text-label-sm` — เลยถูกจัดกลุ่มเดียวกับสี
แล้วโดนลบทิ้งข้างหนึ่งตามกฎ "อันหลังชนะ" โดยไม่มี error ไม่มี warning

```
"bg-primary text-on-primary … text-title-lg"  →  "bg-primary … text-title-lg"   ← สีหาย
"… text-body-md text-on-surface"              →  "… text-on-surface"            ← ขนาดหาย
```

- ปุ่ม `size="lg"` (สีมาก่อนขนาด) → **สีหาย** ตัวหนังสือ inherit สีเข้มมาอยู่บนพื้นเขียว
  = contrast bug ที่กฎ 5-6 ใน CLAUDE.md ห้ามไว้พอดี แต่หลุดมาทางที่ไม่มีใครมอง
- `input` / `select` / chip / แท็บล่าง (ขนาดมาก่อนสี) → **ขนาดหาย** ฟอนต์เลยใหญ่กว่าที่ออกแบบ

แก้ที่ `src/lib/utils.ts` ที่เดียว — `extendTailwindMerge` สอนให้รู้จัก type 8 ขั้น
กับ shadow 5 ตัวของเรา ทุกจุดที่ใช้ `cn()` หายพร้อมกันหมด
มี test กันไว้แล้วที่ `src/lib/utils.test.ts`

> ⚠️ **เพิ่ม `--text-*` หรือ `--shadow-*` ใน `theme.css` เมื่อไหร่ ต้องไปเติมใน `utils.ts` ด้วย**
> ไม่งั้นบั๊กเดิมกลับมาเฉพาะ token ตัวใหม่

**2 · หน้าขายเลื่อนลงไม่สุด — ท้ายจอมุดใต้แท็บล่าง**

หน้าอื่นเป็น `min-h-dvh pb-nav` (เว้นที่ให้แท็บล่างที่เป็น `fixed`)
แต่หน้าขายเป็น `h-dvh` + scroll ข้างใน และไม่ได้เว้นที่ให้เลย
ท้าย list จึงอยู่ใต้แท็บล่างถาวร — เห็นชัดสุดตอนกางฟอร์ม "เพิ่มสินค้าเร็ว" ปุ่มบันทึกโดนบัง
(ตอนมีของในบิลไม่เจอ เพราะแถบสรุปมี `mb-[calc(...)]` ดันตัวเองขึ้นไว้อยู่แล้ว จึงบังอาการ)

- utility ใหม่ `pb-bottom-nav` = ความสูงแท็บล่าง + safe area เป๊ะๆ ไม่บวก 16px เหมือน `pb-nav`

- `<section>` ฝั่งซ้ายของหน้าขายใส่ `pb-bottom-nav md:pb-0` (md ขึ้นไปไม่มีแท็บล่าง)
- แถบสรุปบิลถอด `mb-[calc(...)]` ออก ไม่ต้องแก้เองอีกแล้ว

3. **ต้นฉบับมีเฉดน้ำเงิน 2,214 เฉด** (ไล่โทน + noise) พอ `flatten`/`extend` ด้วยสีเดียว

   ⚠️ ใช้กับไอคอนเท่านั้น — **สีตัวอักษรใน wordmark คือ `#002546` ห่างจาก navy แค่ 15 หน่วย**
   ขยาย threshold เกิน 14 เมื่อไหร่จะไปเปลี่ยนสีโลโก้ทิ้งเงียบๆ
4. **Next ใส่ให้แค่ `mobile-web-app-capable`** (ชื่อใหม่) · iOS ก่อน 16.4 รู้จักแค่
   `apple-mobile-web-app-capable` ต้องใส่เองผ่าน `metadata.other`

**ตรวจแล้วก่อนเปิด standalone:** ทุกหน้าที่ไม่ใช่แท็บหลักมีปุ่มย้อนกลับ/ปิดในแอปครบ

  ใบเสร็จที่ยื่นให้ลูกค้าตอนนั้นยังไม่มีเลขบิล

⚠️ **ยังไม่ได้ทำ:** og-image สำหรับตอนแชร์ลิงก์บิลเข้า LINE

## ค้างอยู่ / ยังไม่ตัดสินใจ

**ต้องทำใน Dashboard (ผมทำผ่าน MCP ไม่ได้) — เรียงตามความเร่งด่วนหลัง deploy**

- 🔴 **ตั้ง Site URL / Redirect URLs ให้ตรงกับโดเมนจริง** (Authentication → URL Configuration)
  Site URL: `https://linchak-pos.vercel.app`
  Redirect URLs: `https://linchak-pos.vercel.app/**` และ `http://localhost:3000/**`
  **ถ้าไม่ตั้ง ลิงก์รีเซ็ตรหัสผ่านและยืนยันอีเมลจะพากลับไปที่ localhost ของคนอื่น**
- ~~เปิด **Leaked Password Protection**~~ — **ทำไม่ได้บน free tier** (Pro plan ขึ้นไปเท่านั้น)
  security advisor จะแนะนำเรื่องนี้ตลอด — ข้ามไปก่อน ไว้อัปเกรดแผนแล้วค่อยเปิด
- ตั้ง **Minimum password length = 8** ให้ตรงกับที่ฟอร์มบังคับ (default ของ Supabase คือ 6)
  ไม่งั้นคนที่ยิง API ตรงจะตั้งรหัส 6 ตัวได้ทั้งที่ UI บอก 8
- ⚠️ **ปิด Confirm email ไว้ชั่วคราวเพื่อความสะดวกตอนพัฒนา** (Authentication → Providers → Email)
  **ต้องเปิดกลับก่อนขึ้นจริง** ไม่งั้นใครก็สมัครด้วยอีเมลคนอื่นได้

- 🚨 **ต่อ SMTP เองก่อนเปิดจริง — เป็นตัวบล็อกการเปิดตัว ไม่ใช่ของแต่ง**
  SMTP ของ Supabase **ส่งได้เฉพาะอีเมลของทีมในโปรเจค** และจำกัด **2 ฉบับ/ชม. ทั้งโปรเจค**
  ไม่มี SLA · เอกสารระบุชัดว่าไม่ได้มีไว้ใช้จริง
  ⇒ ถ้าไม่ต่อ SMTP เอง **ลูกค้าจริงจะไม่ได้รับอีเมลเลย** (ไม่ใช่ช้า — ส่งไม่ออก)

  แผนธุรกิจวาง **Resend** ไว้แล้ว (business-plan §7.2 "Email free tier 0฿")
  free tier = 3,000 ฉบับ/เดือน (100/วัน) · เทียบกับเป้า M24 ที่ต้องใช้ ~400 ฉบับ/เดือน
  ⇒ free tier พอถึงหลังปีที่ 2 ตรงตามที่แผนตั้งไว้
  ตั้งค่าที่ Authentication → SMTP Settings (งานประมาณ 15 นาที)
- ตั้ง **Site URL** = `http://localhost:3000` และ **Redirect URLs** = `http://localhost:3000/auth/confirm`
  (Authentication → URL Configuration) · ตอน deploy เพิ่มโดเมนจริง
